# singlefs-ai-sop-zh

**贡献者治理规范与门禁工具（Contributor Governance），独立分发。**

**它管的是「项目怎么跟 AI 协作」**：提交要带什么证据、文档怎么写才不会被检索误读、
决策记在哪、门禁拒绝时必须给出什么。这几件事跟你在做什么系统没关系。

> **实现上 AI 友好，审核上人类友好。**
>
> 这是整套规范的组织原则，展开见 [rules/engineering-philosophy.md](rules/engineering-philosophy.md)。

singlefs 把这个仓克隆到自己的 `.claude/singlefs-ai-sop/`，这样每个参与者拿到的是
**同一份**规矩、**同一套**门禁脚本、**同一批** skill。一致性靠共用一个源，不靠各自抄。

**它不管的是：文件系统该怎么设计。** 事务、崩溃一致性、盘上格式这一类纪律
（比如「从事务开始」「记账是事务的副产品」）属于项目本地，
放在项目自己的 `.claude/rules/` 里。

一条内容该放上游还是放项目本地，判据写在 [CLAUDE.md](CLAUDE.md) 的「分工判据」一节，
这里不抄第二份——**拿不准就放项目本地**。

## 本仓的变更门槛

**这份 SOP 一旦定下来就该几乎不动。** 它是所有参与者共用的地基，
改一条等于同时改掉所有人的下限，所以改它的门槛要比改项目里任何一处都高。

| 想加/改一条 | 先过这三关 |
|---|---|
| 1 | **它管的是协作吗**——提交证据、文档写法、决策记在哪、门禁怎么回话，这些跟做的是什么系统无关。文件系统设计特有的，该放项目自己的 `.claude/rules/`。拿不准就放项目本地 |
| 2 | **它能变成一个会失败的检查吗**——变不成的先留在项目 kb 里当待议，别写成规矩（见 [rules/sop-first.md](rules/sop-first.md)） |
| 3 | **写得出拒绝时的下一步吗**——`bad` 要带 `howto`，`die` 要带第二个参数，由 `scripts/gate-lint.sh` 强制 |

**这三关靠人判断，不靠门禁。** SOP 是准则，本身不是被测对象；它该不该收一条规矩，
只有人能判（见 [rules/show-me-test.md](rules/show-me-test.md)：门禁证明证据够不够，不证明语义对不对）。
真正该看的信号是**改得勤不勤**：这份东西老是变，说明它的设计有问题，不是说明它在进步。

**日常活儿不在这个仓。** 平时的工作在 singlefs 里：设计决策、不变量、实验、项目本地规则，
全都在项目自己的 `.claude/` 下。这个仓只在真要改规矩时才动，那种时候应该很少。

**版本号的约定**：`0.x` 表示还没定型，随时会改，项目那边要跟着动。
到了 `1.0.0` 之后，`rules/` 应该很少再改——多数「想加一条规矩」的冲动，
正确的去处是项目本地。

改了规范本体就抬 `VERSION`：下游项目下次跑门禁时靠版本戳发现规矩变了，
不抬版本 = 别人无从知道。**「规范本体」管哪些路径，以 `scripts/version-discipline.sh`
里的 `GOVERNED` 为准**——它是唯一的定义，本文不抄第二份，由那个脚本判红。
改了规则还要重译，各语言同版本，由 `scripts/i18n-sync.sh` 判。

**多语言只是分发方式，不是几套不同的规范。** 项目只装其中一份，
根本不用知道别的版本存在——装出来的项目里，规则、skill、agent 桩、kb 骨架、
litmus 模板全是那一种语言。

## 使用者

**只有一个，就是下表里的 singlefs。** 这个仓不为「将来别的项目也许用得上」做设计：
那种设想没有对照，只会让规矩越写越松。

| 项目 | 位置 | 怎么接的 |
|---|---|---|
| **singlefs** —— 从零设计的 COW 文件系统，Rust 写的 | 这个仓的兄弟目录 `../singlefs` | `.claude/singlefs-ai-sop/` 是这个仓的副本；项目本地规则在 `.claude/rules/fs-design.md`，设计决策在 `.claude/kb/decisions.md` |

装完之后项目根会多一个 `.singlefs-ai-sop-version`，门禁拿它跟这个仓的 `VERSION` 比。
对不上就红，提醒项目那边：规矩变过了，先读一遍再跑。

## 里面有什么

| 路径 | 内容 |
|---|---|
| `CLAUDE.md` | **共享规范的入口。** 对话语言、分工判据，以及 `@` 引用 `rules/` 的那份清单 |
| `rules/` | **规矩本身。** 一条一篇，都要能落到某个会失败的检查上 |
| `scripts/` | **门禁脚本，这个仓最重要的部分。** 规矩的可执行形式 |
| `skills/` | Claude Code skill：怎么跑门禁、怎么记决策、怎么做崩溃测试 |
| `agents/` | 共享 subagent 定义。**已纳入治理，当前为空**，约定见 `agents/INDEX.md` |
| `templates/` | 项目侧 `CLAUDE.md` 与 `kb/` 的骨架 |
| `install.sh` | 把这套东西接进一个项目 |
| `GLOSSARY.md` | 术语的跨语言对照表，各语言仓共用一份 |
| `I18N` / `MANIFEST.sha256` | 语言族配置；规则清单（译本的对账依据）|
| `VERSION` | 规范版本号。门禁会检查项目声明的版本跟这套包一不一致 |

**这份 README 不是规范来源。** 规范正文是 `CLAUDE.md` 加 `rules/`，
靠 `MANIFEST.sha256` 对账，逐篇追溯到各语言译本。
README 是各语言仓各自的门面，只指路，不定规矩——
你在这里读到的任何一条规矩，权威版本都在它指向的那个文件里。

## 装到一个项目里

```bash
# 用安装器（会问你要哪种语言，装完顺带跑一次门禁）
git clone https://github.com/faliye/singlefs-ai-sop-install
bash singlefs-ai-sop-install/sop-install.sh --lang zh --dest <你的项目>

# 或者手动：自己 clone 对应语言的仓，再跑 install.sh
cd <你的项目>
git clone https://<host>/singlefs-ai-sop-zh .claude/singlefs-ai-sop
bash .claude/singlefs-ai-sop/install.sh
```

`install.sh` 会铺下面这些东西，**每一步都回读确认，失败就非零退出**：

| 落点 | 内容 |
|---|---|
| `CLAUDE.md`（项目根） | 一层薄壳 + `@` 引用共享规范 |
| `.claude/kb/` | kb 骨架七篇 |
| `.claude/scripts/*.sh` | 包装，`exec` 到共享脚本；里面不写逻辑 |
| `.claude/skills/*/SKILL.md` | 桩，frontmatter 加一句指向共享正文 |
| `.claude/agents/*.md` | agent 桩，同上（`agents/` 现在是空的，所以暂时不会铺） |
| `litmus/`（**项目根**，不在 `.claude/` 下） | 一对现成的 litmus，照抄用 |
| `.singlefs-ai-sop-version`（项目根） | 版本戳 |

**已存在的文件一律不覆盖**，只报告差异。版本戳只在**没有一份落后于上游**时才刷新——
刷了就等于替项目声明「已经是新版了」，而它的骨架还是旧的。

kb 骨架、skill 桩这些本来就是给项目改的，改过之后就不该再算「落后」。
项目把接管的那几份写进 `.claude/install-owned`，一行一条 `<相对路径>  # 为什么`，
`install.sh` 便不再拿它们跟上游比。**代价是此后上游对它们的改动都不会再送到**——
理由那一栏就是让人正面对上这一点。清单坏了（没写理由、或者写了 `install.sh`
根本不铺的路径）当场判红，不许带着一份读不准的清单去刷版本戳。

## 为什么规范要独立成仓

因为 [rules/show-me-test.md](rules/show-me-test.md) 那条准入铁律——**判据是自动化验证**——
只有在大家跑的是同一套门禁时才成立。各项目各维护一份 `.claude`，
三个月后就会有人说「我这边是过的」，那条铁律当场就废了。
**提交的人也就不知道自己该验到什么程度**，而那正是门禁本来要替他回答的问题。

## 多语言：按自己的语言选用

**开发者按自己的语言挑版本。** 现在有中文、英语、日语，还有别的在做，默认是英语。
装哪种语言的仓就用哪种语言干活：用中文的不用去学英文，用日文的不用读中文。
**AI 也就不用再翻一道**——它在哪种语言的仓里工作，就用那种语言协作，
少转述一次就少丢一次信息。多语言存在的理由就是这个。

`I18N` 里 `this=` 是本仓的语言，`default=en` 是默认版本，
`languages=` 是已发布的语言，`reference=` 指明清单与门禁脚本维护在哪一个仓（现在是中文仓）。

**现状：中文之外的版本先用机器翻译铺开，规范定版之前会做精确翻译。**

真正能消歧的是 `scripts/`：**各语言读起来不一致时，以脚本的实际行为为准。**
脚本是这套规则唯一没有歧义的表述。这也是 `sop-first.md` 要求
「一条规则要能变成一个会失败的检查」的第二个理由——**能变成检查的规则，翻译不走样。**

### 一种语言一个仓，目录名统一

```
singlefs-ai-sop-en     英语（默认版本）
singlefs-ai-sop-zh     中文（清单与脚本放在这儿）
singlefs-ai-sop-ja     日语
```

更多语言版本开发中。

已发布的语言列在 `I18N` 的 `languages=` 里。各语言不放同一个仓：
塞进一个仓会让它随语言数量越长越大，而「薄」正是这个仓的卖点。

项目安装时**只 clone 自己那一种**，目录名统一：

```bash
git clone https://<host>/singlefs-ai-sop-ja .claude/singlefs-ai-sop
```

目录名一样，所以 `@` 引用的路径和脚本包装**一个字都不用改**：换语言就是换个 clone 源。

### 一次贡献要覆盖全部已发布语言

**不管你用哪种语言写，提交都必须同时改到所有已发布的语言版本，一起合并。**
只带自己那一种语言的提交不收——那等于把「让别的语言的人拿到旧规则」的代价推给别人。
理由是这个仓自己的规矩（见 `kb-discipline.md`）：**矛盾比空白更糟**。
只要有一次「先改这份，别的下次再说」就会分叉，而用另一种语言的人不知道自己读的是旧的。

**哪一份写得不清楚就改哪一份**，顺便回头看看别的版本是不是也不清楚。
不同语言暴露出来的含糊之处不一样，这是多语言并存顺带的好处，别浪费。

**各版本说的是不是同一件事，由改的人自己保证。** 门禁只看得出哪几篇哈希对不上
（见 [rules/show-me-test.md](rules/show-me-test.md)：门禁证明证据够不够，不证明语义对不对）。

对账靠 `MANIFEST.sha256`，里面记着**每一份含给人读的散文的文本**的路径和哈希：
`CLAUDE.md`、`rules/`、`agents/`、`skills/`、`templates/`（连 `*.litmus` 一起）。
判据只有一条：**里面有没有给人读的散文。** 有就翻译，没有就原样复制。
两边都不沾的会被 `scripts/manifest.sh` 的覆盖率检查拦下来，「忘了纳入」不许静默通过。
其余语言的仓各抄一份存成 `SOURCE-MANIFEST.sha256`，
之后比两份清单就知道哪几篇落后了。
这个仓因此只多 `MANIFEST.sha256` 和 `I18N` **两个小文件**，还是单语言、还是薄的。

改了清单覆盖的任何一篇，就要跑 `bash scripts/manifest.sh --update`，
否则门禁会红——**清单不更新，等于每一份都显示「最新」，而除了刚改的那份其实全落后了。**

## 更新规范

项目更新完副本，跑一次 `bash .claude/scripts/gate.sh`，版本对不上会报出来。
