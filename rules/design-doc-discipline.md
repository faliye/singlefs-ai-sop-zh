# 设计文档铁律

**管的是**：README、设计说明、`records/`，也就是**给人从头读的东西**。

这类文档就该讲清来龙去脉、把道理说透，不用为机器让路。
写得好读是目标，不是将就。给模型检索的知识文档另有一套，见 `kb-discipline.md`。

## 1. 正文只写当前现状，历史一律放到文末

正文里不许写「原先是 X、现在改成 Y」「以前叫 A」这类话。
要留的历史统一放到文末的「历史版本」一节：

```markdown
## 历史版本

### YYYY-MM-DD
- 曾经 X / 现在 Y / 改动依据：Z
```

**为什么**：正文里混着历史，读的人一眼分不出哪个是现在的值。
叠几轮下来，连「现在是什么样」这种最基本的问题都得翻旧账才能回答，
而翻出来的结论还经常是错的。这个项目要做好几年，翻旧账的成本会越滚越大。

**推论**：
- 改了某个决定就**直接改正文**，别在旁边加一句「（原为 X）」。
- 结论被推翻就**把旧结论从正文删掉**，「曾经 X / 现在 Y / 推翻依据」写到文末。
- 正文里不许出现 `~~删除线~~`、`〔已废弃〕`、`（已被 XX 覆盖）` 这种就地标注。
- 代码注释也一样：写「现在为什么这样」，不写「以前怎样」。
  **例外是检查代码里记坑的注释**。「这个绕法实测能过，所以才有这条检查」
  说的是这条检查**现在为什么存在**；删掉它，下一个人会觉得这检查多余而删掉。
  判据看它指向什么：指向**这段代码现在为什么长这样**就留，
  指向**一个已经不存在的旧版本**就删。

`CLAUDE.md` 和 `rules/*.md` **连文末的历史版本都不留**，历史一律放 `CHANGELOG.md`。
它们是每次开工都要通读的规矩，混进历史会冲淡。

由 `scripts/doc-lint.sh` 强制。

## 2. 长度要配得上改动的重量

判据与尺子都在 `writing-discipline.md` 的「长度要配得上改动的重量」一节，这里不抄第二份。

## 3. 该说服人的地方就好好说服

设计文档要回答两件事：为什么该这么做，以及怎么上手。
这两件事需要铺垫、需要例子、需要把取舍摊开讲，**这些都不算废话**。

判据：删掉这一段，读的人还会不会同意？还上不上得了手？
都还行就删得；不行就说明这段有用。
