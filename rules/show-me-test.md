# 准入铁律：Show me test

> **Make every submitted patch review-worthy.**
>
> 让每一份提交都值得被 review。
>
> **Contribution throughput may be unbounded; acceptance throughput is evidence-bound.**
>
> 投稿吞吐可以无限，接收吞吐受证据约束。

**这是这个项目和 Linux 内核最大的不同，也是最重要的一条规则。**

## 门禁是抬地板的，不是筛人的

上面第一句是目的，第二句是理由，次序不能颠倒。

**门禁不是为了把谁挡在外面，是把每一份提交抬到「值得花人的时间去看」那条线上。**
机械的那部分——有没有测试、声明和实测对不对得上、文档和实现同不同步——交给脚本做完，
人的注意力才腾得出来，用在只有人能判的地方：**这个测试测的是不是对的东西**。

第二句说的是为什么非这么做不可。不管提交从哪来，供给只会越来越多，
而人能 review 的量没变。**跟得上这个增长的只有证据。**

反过来看，一份不带证据的提交，会占掉别人的时间去问「你验过吗、怎么验的」。
门禁把这一来一回提前到提交者自己机器上，**对双方都省事，不是刁难**。

## 判据是测试

**patch 收不收，由自动化验证说了算。** 每个 patch 都该认真测过；
**认真测过、负责任的提交，我们都欢迎。**

门禁过就是过，不过就是不过。这对提交者其实是保护：
你的 patch 能不能进，取决于验得够不够扎实，跟你是谁没关系。

## 没有测试的 patch 一律不收

**改了 `crates/*/src/` 就得带测试。** 没有例外，没有「这个太简单了」，
也没有「下个 patch 补上」。只改文档和脚本除外。

由 `scripts/show-me-test.sh` 强制（`gate.sh` 把它当一个阶段跑），不靠自觉。

## 新增的测试必须先证明它会红

**每个「验证」都得能失败。** 写完自己问一句：这段代码真坏了，我的检查会不会报警？

做法是：**先把被测代码改坏，看着测试变红，再改回来。**
证明不了会红的测试，等于没写。

脚本查不了这一步——它只能看出有没有测试。所以**在 commit message 里写明
你是怎么确认它会红的**：改坏了哪一行，看到哪个断言失败。写不出来就是没做。

有变异 harness 的仓要再进一步：把「改坏哪里 → 哪条断言红」做成**存进仓里的变异清单**，
交给门禁反复复跑。commit message 里的叙述是没有 harness 时的退路，不是首选——
叙述只被读一次，存进仓的清单每次复跑都在重新证明。

**这条同样管设计论证**：对抗轮打中的每一条，先在模型里做成一个**必须报非 0** 的世界，
再改规则。不然改法对不对，没有任何东西验得了——改完照样全绿，因为那个错本来就没人测。

## 踩过的坑要做成会失败的检查，不要做成提醒句

写一句「注意别在 X 的时候做 Y」，拦不住手敲命令的人。
**能拦住的是一个当场拒绝执行的检查。**
踩到新坑，第一反应该是「这条怎么做成门禁里会红的一项」，不是「这条写进哪个文档」。

### 但要先问这个坑在哪一层：装置里，还是口径上

**立在一个装置里的检查，管不住下一个装置。** 断言与变异测试都只在它所在的那套装置里生效；
换一套装置从头把同一件事再建一遍模型，那条检查一个字都不会说。

实测（2026-09-06）：一个计数模型把「容量 × 填充率」那笔预算当成了其中一类对象的数量、
再往上加另一类，等于往盘上摆了 126% 的对象。当天就修好了，还留了一条会红的断言守着。
**几小时后另一个模型重犯了同一个错**（这次是 135%），而那条断言在另一套装置里，一声没吭：
新装置自己的单测全绿、变异全抓、门禁全绿，两个模型对**同一个物理量**报的数差 1.5 倍，
没有任何东西去对过。错的那个数还被写进了一条已定条款。

⇒ **判据不是「这个坑做没做成会红的检查」，是「这个坑在哪一层」**：

| 坑在哪 | 检查立在哪 |
|---|---|
| 一段代码的行为里 | 那段代码旁边就够 |
| **建模口径上**（同一个量该怎么算、边界算不算、单位是什么） | **立在装置之间**：两套装置算同一个量，就要有一条检查逼它们落到同一个数；对不上判红 |

**快速判据**：换一套装置、从头把同一件事再做一遍，还会不会再踩一次？
会 ⇒ 它在口径层，检查跨装置才有用。
⚠️ 修坑的人最容易在这里收手：他确实把坑做成了会红的检查，**证据齐全、门禁全绿**，
所以不会再想一遍这条检查的射程有多远。

## 最终判据是 QEMU/KVM 压测

单元测试和模型对拍只是快速反馈，**不是准入标准**。
准入标准是在 QEMU/KVM 里跑真实负载加崩溃注入，跑完 checker 全绿。

## 门禁不许假装通过

没实现的门禁阶段要**明说没实现**，不许悄悄跳过。
一个偷偷没跑崩溃测试的绿门禁，比红门禁危险得多。

同理，**跑批脚本不许把单轮的失败吞掉**（`|| true` 那种），输出路径也不许跨轮复用。
这两样凑一起，失败的那轮会安静地拿上一轮的输出顶上——看着一切正常，只是数字不动。
判据是「这份输出能不能证明是这一轮产生的」：跑之前删掉旧输出，跑完认一个本轮才会出现的完成标记。

**扫到 0 项也不是通过。** 判据的搜索范围写窄一点，对象就会全被第一步跳过——
既不算通过也不算失败，末尾照样报绿，而没人看得出来。
⇒ 扫一批对象的检查，成功那句里要报出**检查了多少项**；`gate-lint.sh` 判这一条。

**项目本地阶段与共享阶段同规矩。** 它们一样会拒绝提交者，所以一样受 `gate-lint`
与 `shell-lint` 管——`gate.sh` 把 `.claude/gate.d/` 一并交给这两个 lint。
（此前它不在任何一个 lint 的扫描里，一喂就是 7 条没有出路的拒绝。）

# 门禁能证明什么，不能证明什么

> **Gate proves evidence requirements, not semantic correctness.**
>
> 门禁证明的是证据要求被满足，不是代码语义正确。

这条是上面「让每一份提交都值得被 review」的必要配重。少了它，「门禁全绿」
会被读成「代码是对的」，而那正是这个项目最怕的那种没人察觉的错误。

## 能通过全部门禁、却仍然是错的

| 情形 | 门禁为什么看不见 |
|---|---|
| 测试测的是实现，不是契约 | 门禁只数有没有测试，不判测得对不对 |
| litmus 声明本身写错了 | 声明 Sometimes、实测 Sometimes → 判「符合」。**除非有对照组**，否则什么也没证明 |
| 不变量本身就是错的 | checker 会老老实实检查一条错规矩，而且全绿 |
| 覆盖的不是出问题的那条路径 | 覆盖率不是正确性 |
| 正文引的数与它自己的产物对不上 | 复跑的**区间**断言只钉住结论落在哪一档，不钉正文里的那个数：区间有多宽，正文就能漂多远（实测：正文写 1.475×，同一份留存产物里是 1.625×，区间是 [1.15, 2.10]，全绿）|
| 两套装置对同一个量算出不同的数 | 断言与变异只在**一套装置内部**生效，跨装置没有任何东西在对 |
| 设计本身就错了 | 门禁根本够不着这一层 |

## 推论

1. **门禁绿不等于可以不看代码。**
   它的用处是把人从「找有没有测试」里解放出来，
   去看**测试测的是不是对的东西**——那才是只有人能做的事。

2. **语义对不对，写在 `kb/decisions.md` 和 `kb/invariants.md` 里，不在门禁里。**
   门禁只保证这两样**写下来了、实现了、而且和代码同步**。
   它们本身写得对不对，靠人。

3. **门禁是下限，不是上限**（`rules/sop-first.md`）。
   它保证没人低于某条线，不保证谁做对了。

4. **没实现的阶段要一直列出来。**
   少一个验证手段，就等于有一整类错误从来没人看过。
   `gate.sh` 每次都打印这份清单，就是不让人把「过了」当成「验过了」。

## 为什么是这条规矩

**提交的量在变得没有上限，而人能 review 的量没变。**

不管提交从哪来——更多的人、更好的工具、更强的自动化——供给只会越来越多。
「靠人一行行读代码」这个办法跟不上。跟得上的只有**自动化验证**：
它不管 patch 从哪来、写得多漂亮，只管跑不跑得过。

## 把判据放在证据上，正是为了不按来源区别对待

**按来源分类审查才是歧视，而且它还不好使。**

一旦按提交的人是谁来定审查松紧，就是拿身份代替了证据——
**而一个 patch 不会因为作者是谁而变好或变坏**。
身份这个指标很差：既冤枉认真的新人，又放过随手提交的熟人。

证据不一样。它对所有人是同一把尺子，而且**提交的人自己就能先量一遍**：
发出去之前跑一遍门禁，就知道自己站在哪。这一点身份判据永远做不到。

所以这个项目**不按来源分类**，也不给哪一类单开规矩。
只分两种：**带证据的提交，和不带的。**

**所以门禁的质量就是这个项目的上限。** `scripts/` 比任何一个 crate 都重要。
