# 机器优先：先分清「可读」与「可验证」

软件工程里很多通行的准则，前提都是**「一个人得把整套东西装进脑子里」**。
这个前提正在失效：代码是人和模型一起写出来的，而读代码这件事本身也能交给模型。

**这个项目不默认照搬这些准则。** 每一条都重新过一遍判据，过不了的就不要。

## 态度：先怀疑，别照单全收

对现成「最佳实践」的默认态度是**存疑**，不是遵守。

理由很简单：**这些准则里有相当一部分，本来就是在人脑算力有限的前提下，
用来托住工程质量下限的**。它们对标的是人的极限。
而现在机器的算力早就超过那条线了，照着旧极限定的下限，现在就太低。

不是说它们都错——是说它们的**理由要重新查一遍**，
不能因为「大家都这么做」就接着做。

## 这条姿态的前提，以及怎么推翻它

「机器的算力早就超过那条线」是整套做法的地基。**这是一句能被观测推翻的经验判断，不是信条。**
所以这里写清它靠哪两条前提撑着、什么现象会推翻它。
**要反驳这套做法，靶子是这两条前提，不是下面「放宽的」和「留下的」那两张表。**

### 前提一：上下文窗口已到 2×10⁵ ~ 10⁶ token 量级

200K / 500K / 1M 三档。1M 那一档能一次装下一个 crate 加上它的测试、kb 和决策记录。
依据：这个仓这一轮工作就跑在 1M 的会话里。别家的数字不写进来——现查不了的数字不算证据。

**口径**：这说的是**宣称的窗口上限**，不是「整个窗口里准确率都一样」。
长上下文中段记不牢是已知现象，这个项目没实测过它从多大规模开始碍事。

- **它撑起的**：放宽「PR 要小」「概念要少」「DRY 靠人同步」这三条。
  它们原本的理由都是「一次装不下」，而在 1M 那一档，这个理由不再自动成立。
- **它撑不起的**：「推理范围要有界」不在放宽之列。窗口大了，但**还是有限**，
  而且离得越远越记不牢。所以模块边界和显式契约比过去更值钱，不是更不值钱。

### 前提二：并发交错已经可以被穷举判定

「这个屏障够不够」这类问题，**靠直觉给不出能复核的答案**。现在它拆成两半：

| 谁做 | 做什么 | 精度 |
|---|---|---|
| herd7 / LKMM | 在给定内存模型下**穷举**所有允许的交错，给 Never / Sometimes 判定 | 对写下来的那个 litmus 是完备的 |
| 模型 | 把代码里的同步模式翻成 litmus、枚举该问哪些场景 | **不完备——缺口在这里** |

**口径**：精确的是工具，不是模型。工具只回答你写下的那个 litmus，
至于「有没有漏掉一个该问的场景」，没有任何东西能保证。
所以 `scripts/lkmm.sh` 强制**每条 Never 都有自己的对照组**（同名前缀 + 声明 Sometimes）：
只有 Never 而没有与它配对的那一条，就分不清是屏障挡住了，还是这个模式本来就撞不上。
全局有几条 Sometimes 不算数——它们回答的不是这一条的问题。

- **它撑起的**：「穷尽性能被机器检查」，以及由此推出的「宁可写穷举的显式分支」
  和「控制流路径数有限，才验得完」。写法落在 `code-discipline.md` 的「分支」与「函数与嵌套」两节。

### 前提失效时，收回哪几条

前提不是永久的。观测到下面任一现象，对应的放宽当场收回：

| 观测到什么 | 收回什么 |
|---|---|
| 在这个项目的实际规模上，模型漏掉了一条已经在上下文里的约束 | 收回「PR 要小」的放宽，重新按装得下的粒度切 |
| 生成出来的重复代码和生成器对不上 | 收回「DRY」的放宽，回到不许重复 |
| litmus 的判定和真机压测的结论对不上 | 收回「穷尽性能机检」，`lkmm.sh` 降为参考，不再当门禁 |

**这张表就是这份规则自己的反推**（见 `evidence-discipline.md`）：
说不出「什么现象会推翻它」的前提，不是前提，是信仰。

## 遇到一条通行准则，走这个流程

1. **问它当初要解决什么问题。** 说不出来就直接放弃——
   说不出理由的规矩，本来也守不住。
2. **问那个问题今天还在不在。** 如果当初解决的是「人记不住」「人读不过来」
   「review 忙不过来」，那多半已经不在了。
3. **问它有没有第二个理由。** 不少规矩顺带还解决了一个跟人无关的问题
   （见下面「留下的」那张表）。有就留下，**并且把理由改成那个**。
4. **改过的理由要能落成门禁。** 落不成的降为建议，不写成规矩。

## 判据

> **这条规则是让代码更容易被机械验证，还是只让它更容易被人眼扫过？**

- 只是让人看着舒服 → **可以放弃**
- 让验证更容易 → **留下，但理由要重写**。别再挂在「可读性」上：
  挂在可读性上的规矩，下次有人问「为什么」的时候就守不住了。

## 审完的结果放在哪

**代码怎么写**（名字、分支、类型、函数与嵌套、注释、重复）逐条审过的结果，
连同每一条的写法，在 `code-discipline.md`，那里是唯一的一处。
**设计与流程层面**的准则在下面两张表里。

## 放宽的（人脑带宽的产物）

| 旧准则 | 它原本的理由 | 处置 |
|---|---|---|
| 设计要统一、概念要少 | 维护的人要装得下 | **放宽**。「一棵树装下所有东西」就是这么来的 |
| PR 要小 | review 忙不过来 | **放宽**。但能二分、能回退还是要保 |

⚠️ **放宽的是「为了让人装得下而做的压缩」，不是「把含义写明白」**——后者对模型同样有好处。
见 `engineering-philosophy.md` 的「AI 友好 ≠ 不可读」。

## 留下的（与谁读代码无关）

| 准则 | 真正的理由（重写过的） |
|---|---|
| 崩溃一致性、不变量 | 这是物理，不是心理 |
| 磁盘格式兼容 | 对外的永久承诺，改不掉 |
| 测试可复现 | 任何判断的前提，人和机器都一样 |
| 故障域隔离 | 一个 bug 波及多大，跟谁读代码无关 |
| 可二分、可回退 | **改动越大这两条越值钱**，不是越不值钱 |
| 模块边界要有明确契约 | **没有契约就没法单独验一块** |
| 推理范围要有界 | **要能增量验证，推理范围就得有界；上下文窗口也是有限的** |

最后两条最容易被当成「可读性」一起丢掉。它们不是。

## 一条反向的提醒：文档纪律不在放弃之列

`writing-discipline.md` 那一套——正文只写现状、历史放文末、决策记录进 kb——
**不是为了迁就人脑带宽才有的**。

一份混着历史的文档，**模型比人更分不清哪个是现在的值**：
它没有「我记得上周改过」这种线索，只能全盘当真。
过时或者自相矛盾的文档，对模型的害处不比对人小，只会更大。

同理，`kb/decisions.md` 的价值是在涨不是在跌——
它是唯一能告诉后来的人（或模型）「这条为什么是现在这样、依据是什么」的地方。
