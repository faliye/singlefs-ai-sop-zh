# 机器优先：先分清「可读」与「可验证」

**这个项目不默认照搬软件工程里的通行准则。** 每一条都重新过一遍判据，过不了的就不要。

## 态度：先怀疑，别照单全收

对现成「最佳实践」的默认态度是**存疑**，不是遵守：每一条的理由重新查一遍，不因为「大家都这么做」就接着做。

## 这条姿态的前提，以及怎么推翻它

整套做法靠两条前提撑着。**要反驳这套做法，靶子是这两条前提，不是「放宽的」和「留下的」那两张表。**

### 前提一：上下文窗口已到 2×10⁵ ~ 10⁶ token 量级

200K / 500K / 1M 三档。1M 那一档能一次装下一个 crate 加上它的测试、kb 和决策记录。
别家的数字不写进来。

**口径**：这说的是**宣称的窗口上限**，不是「整个窗口里准确率都一样」。
长上下文中段记不牢从多大规模开始碍事，这个项目没实测过。

- **它撑起的**：放宽「PR 要小」「概念要少」「DRY 靠人同步」这三条。
- **它撑不起的**：「推理范围要有界」不在放宽之列。

### 前提二：并发交错已经可以被穷举判定

「这个屏障够不够」这类判定拆成两半：

| 谁做 | 做什么 | 精度 |
|---|---|---|
| 工具 | 在给定的形式模型下**穷举**所有允许的交错，给出判定 | 对写下来的那个形式模型是完备的 |
| 模型 | 把代码里的同步模式翻成形式模型、枚举该问哪些场景 | **不完备——缺口在这里** |

**口径**：精确的是工具，不是模型。「有没有漏掉一个该问的场景」「写下的和代码今天做的是不是一回事」，没有任何东西保证。

用哪个工具、怎么证明它的判定分得出差别、怎么把写下的模型绑到代码上，
**由项目自己定、自己测、自己验**，写在项目本地规则里。共享门禁不带这一层。

- **它撑起的**：「穷尽性能被机器检查」，以及由此推出的「宁可写穷举的显式分支」
  和「控制流路径数有限，才验得完」。写法落在 `code-discipline.md` 的「分支」与「函数与嵌套」两节。

### 前提失效时，收回哪几条

每条前提都在这张表里有一行，写出什么观测会推翻它。观测到哪一行的现象，当场收回同一行的放宽：

| 观测到什么 | 收回什么 |
|---|---|
| 在这个项目的实际规模上，模型漏掉了一条已经在上下文里的约束 | 收回「PR 要小」的放宽，重新按装得下的粒度切 |
| 生成出来的重复代码和生成器对不上 | 收回「DRY」的放宽，回到不许重复 |
| 项目用来穷举交错的工具，判定和真机上的结论对不上 | 收回「穷尽性能机检」，那个工具降为参考，不再当门禁 |

## 遇到一条通行准则，走这个流程

1. **问它当初要解决什么问题。** 说不出来就直接放弃。
2. **问那个问题今天还在不在。** 当初解决的是「人记不住」「人读不过来」
   「review 忙不过来」的，多半已经不在了。
3. **问它有没有第二个理由**：跟人无关的那种（例子见「留下的（与谁读代码无关）」）。
   有就留下。
4. **改过的理由要能落成门禁。** 落不成的降为建议，不写成规矩。

## 判据

> **这条规则是让代码更容易被机械验证，还是只让它更容易被人眼扫过？**

- 只是让人看着舒服 → **可以放弃**
- 让验证更容易 → **留下**。

## 审完的结果放在哪

**代码怎么写**（名字、分支、类型、函数与嵌套、注释、重复）逐条审过的结果，
连同每一条的写法，在 `code-discipline.md`，那里是唯一的一处。
**设计与流程层面**的准则在「放宽的（人脑带宽的产物）」与「留下的（与谁读代码无关）」两节里。

## 放宽的（人脑带宽的产物）

| 旧准则 | 处置 |
|---|---|
| 设计要统一、概念要少 | **放宽** |
| PR 要小 | **放宽**。但能二分、能回退还是要保 |

⚠️ **放宽的是「为了让人装得下而做的压缩」，不是「把含义写明白」**。
见 `engineering-philosophy.md` 的「AI 友好 ≠ 不可读」。

## 留下的（与谁读代码无关）

- 崩溃一致性、不变量
- 磁盘格式兼容
- 测试可复现
- 故障域隔离
- 可二分、可回退
- 模块边界要有明确契约
- 推理范围要有界

## 一条反向的提醒：文档纪律不在放弃之列

`writing-discipline.md` 那一套（正文只写现状、历史放文末、决策记录进 kb）不在放宽之列。
