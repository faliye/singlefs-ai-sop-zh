# 工程理念

> **实现上 AI 友好，审核上人类友好。**

这不是在两个目标之间折中，而是**两条本来就该分开的轴**。

过去它们是一条，写代码的和读代码的是同一批人，「好写」和「好读」只能是同一件事。
现在不是了。

## 两条轴各自优化什么

| | **实现面：AI 友好** | **审核面：人类友好** |
|---|---|---|
| 谁在用 | 模型写、模型改、机器验 | 人做判断、人担责任 |
| 优化什么 | 可机检、可穷举、可强制进入、可回退 | 可判断、可信、看得出取舍 |
| 具体形态 | 显式穷举分支胜过聪明的通用路径；类型让非法状态无法表示；不变量写成断言；宁可生成重复也不手工维护 | 决策带依据；门禁失败带下一步；数字带口径；未验证的显式标出 |

## AI 友好 ≠ 不可读

对模型友好的方向是**更显式**，不是更晦涩。

一段没有命名、没有类型、嵌套七层的代码，模型读起来不比人轻松：它拿到的信息更少，
出错更多，而且错误更难被发现。砍掉可读性不会让实现更适合 AI，只会两边都变差。

放宽的只有一样：**为了让人脑装得下而做的压缩**，比如「一个机制包打天下」「概念越少越好」
这类设计上的统一性要求。

下面四项**不在放宽之列**。它们看着像可读性，其实是可验证性或者信息量：

| 项 | 为什么留下 |
|---|---|
| 命名 | 命名是信息，不是装饰：省掉的语义，模型读了实现也补不回来 |
| 函数职责单一 | 一个函数做一件能单独验证的事。长度按这个定，不按屏幕高度定 |
| 路径数有限 | 全覆盖这段代码的控制流要多少个用例？答不出、或者无限，就验不了。量的是路径数，不是嵌套层数；它是能验的必要条件，不是充分条件 |
| 约定一致 | 约定不一致会让机器检查失效。这和「设计统一性」是两回事，别混 |

判据还是 `machine-first.md` 那一条：这条规则是让代码更容易被机械验证，还是只让它更容易被人眼扫过？
上面四项都属于前者，留下，但理由要改写成验证和信息量，不再挂在「可读」上。
**落到代码上怎么写，细则在 `code-discipline.md`**：名字不限长度、不用缩写、不用单字母；
层数不限而路径数要有限；语义能进类型就不进名字，能进名字就不进注释。

## 推论：人的注意力该花在哪

人的注意力是这套体系里最贵的东西，别花在读代码上——那件事交给模型。

该花在这四件机器判不了的事上：

1. **这个测试测的是不是对的东西**
2. **这条不变量本身对不对**
3. **这个决策的依据成不成立**
4. **要不要接受这个取舍**

这四件都不用通读实现，但都要求**给人看的那一面对人友好**。

所以门禁的输出、kb 的结论、决策记录、失败信息，都要为人优化，而且比过去更用力——
它们现在是人唯一会看的东西。代码写得难读可以接受，这四样让人判断不了不行。

## 两条轴的分界线

> **Gate proves evidence requirements, not semantic correctness.**

这句话就是分界：机器证明证据够不够，人判断语义对不对。
往下是实现面，往上是审核面。

## 这两面各写在哪

| 面 | 写在哪 |
|---|---|
| 实现 | `machine-first.md`、`code-discipline.md`、`kb-discipline.md`，以及各项目自己的设计纪律 |
| 审核 | `sop-first.md` 的 howto 要求、`design-doc-discipline.md`、决策记录的依据要求 |
| 分界 | `show-me-test.md`「门禁能证明什么，不能证明什么」 |
