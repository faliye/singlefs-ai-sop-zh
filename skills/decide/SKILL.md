# 记一条设计决策

规则在 `rules/kb-discipline.md`，以及项目本地关于格式/结构演进的规则（若有）。

## 状态只有三种

| 状态 | 含义 |
|---|---|
| **已定** | 方向和细节都定了，可以照着写代码 |
| **半定** | 方向定了，细节还没定。**必须写清没定的是哪一条**，否则跟待定没区别 |
| **待定** | 没定。要写清「要定它，得先回答什么」 |

## 写进 `kb/decisions.md` 的格式

```markdown
## D<n> <决策名> —— <状态>

<结论一句话，用祈使或断言，不要用「我们可能会」。>

依据：<为什么。别家的实测数字要带来源与口径，标明未在本工程验证。>

**未定**：<半定时必填，写清缺口。>
```

## 硬要求

1. **改决策必须写清凭什么推翻**，旧结论挪到文末「历史版本」，正文里不留。
2. **改格式就得同时更新 `kb/invariants.md` 和 checker。** 三者对不上的 commit 不收。
3. **定一条决策之前，先把 `kb/pitfalls.md` 对一遍**，确认没踩回同一个坑。
4. 决策之间有牵连的，**两边都注明**，别只写一边。
5. **定完之后发现真正撑着它的理由变了，也算一次决策变更。** 实验经常把「当初给的理由」
   换成另一条更决定性的。把正文里的依据换成实测那条，记进变更史，状态不动也要记。
   正文只留当初那句话的话，三个月后没人知道现在到底是什么在撑着它。
6. **动了由人拍板的那一句，要在 `kb/checks-owed.md` 记一笔未还的账。**
   只在正文写「待复核」，没有任何东西保证它会被看到——而拍板的人不知道自己的定案变了。
   账要点名是哪条决策的哪一项；复核过了才还账。

7. **待定项的问法必须只有一种读法。**
   判据：把问法的每一种读法各写一遍，答案一样吗？不一样就是问法还没定完——
   **先定问法，再谈依据**，否则论证会全打在依据上，而那一格根本不在那儿。

   实测：一格卡了三天、走了两轮论证，真正的原因是问法「它要不要与 X 同等完整性」有两种读法
   （问这个东西**自己的字节**，还是问它**指向的目标**）；当初撤回的那条依据答的是前一种，
   而措辞问的是后一种，所以「那条依据成不成立」怎么判都落不到这一格上。
   把问法定死之后，那一格当场收口——**定的不是依据，是问题**。

## 什么时候该定，什么时候该拖

判据是：**这条决策会不会改变「第一段代码长什么样」。**

会就现在定，拖着做要返工。
不会就可以拖，标成待定，并写清「要定它得先回答什么」。
